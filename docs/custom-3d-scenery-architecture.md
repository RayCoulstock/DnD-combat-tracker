# Milestone 4C: custom 3D dungeon scenery

## Inspection and staged implementation

The dungeon schema is strict version 1 with one `props` collection, ten enumerated procedural types, canonical walls and logical doors. Generation uses those same procedural types. `DungeonBuilder` submits validated map commands; `editMap` owns bounded map-only undo/redo. PostgreSQL stores independent encounter map documents/history and campaign templates; Socket.IO uses encounter/campaign revisions and recipient snapshots, omitting unchanged maps on combat updates. The 4B loader/cache coalesces authenticated GLBs, normalises/grounds models, clones independent skeletons/transforms and disposes shared resources by reference count. Asset delivery grants players only visible references in their active encounter; deletion already locks miniature references.

Implement A: prop variant, version compatibility, additive reference persistence; B: shared model renderer for scenery; C: existing editor/library picker, preview and properties; D: authoritative asset validation/grants/template isolation; E: map-history references, browser/security/restart regressions and guide. Begin on the clean playable-miniatures branch. Preserve all existing tests and procedural generation semantics.

## Document and coordinates

Keep one `props` collection. Add discriminated `type: "asset"` props with stable instance ID, asset UUID, label/category, X/Z position, Y rotation in degrees, uniform scale, verticalOffset and visibility. Procedural variants remain unchanged. Versions 1 and 2 are accepted; old documents remain version 1 until an explicit scenery placement upgrades them to 2. Version 1 cannot contain uploaded scenery; unknown future versions fail safely. Version 2 retains the exact floors/walls/doors structure and can mix procedural/custom props. No binary/model URL is serialised. Generation continues producing version-1 procedural documents with its existing seeded algorithm.

Positions reuse the current cell-centre convention: world X/Z = position minus half map size plus 0.5. Snapping uses integer cell indices; free positioning uses fractional indices within 0..width-1 and 0..height-1, retaining a half-cell border margin. Y is a bounded vertical offset, not terrain elevation or gravity. Central shared scenery limits bound scale, offset and instance count. Anchors are validated; model geometry may extend outside the map. Architectural GLBs are decorative only: they do not create logical walls, collision or door states. Future skins must reference existing logical entities rather than duplicating them.

## Editing and rendering

Add a DM-only 3D Scenery tool using AssetLibrary picker/preview. Left-click places; default snapping is on, free placement optional. Raycast the existing floor pick plane and show a translucent GLB ghost, or a placeholder while unavailable. Middle rotation/right pan/wheel zoom retain camera controls. Escape cancels placement/movement/selection. Selected scenery has a visible outline plus a labelled properties panel. Edit coordinates, rotation, scale, Y offset and visibility; reset, duplicate or remove. A move-to-pointer tool commits one command per placement, not per pointer event. Transform changes affect only the selected instance.

Extract a shared cached model-instance renderer from 4B rather than adding a loader or Canvas per object. Miniatures, placed scenery and placement ghosts use the same cache, SkeletonUtils cloning, normalisation and resource lifecycle. Ghost materials are instance-owned translucent copies and never mutate shared source materials. Cache identity includes authenticated scope and encounter context. Original GLBs are immutable; missing/loading/budget failures display selectable placeholders and explicit retry. Memoised map geometry survives unrelated combat updates, and scenery/miniatures can share one asset download.

## Authority, persistence and deletion

Extend the existing map command union with place/update/duplicate/remove. Existing role, membership, envelope idempotency, encounter revision and transaction checks apply. New explicit placements require ready assets owned by the campaign DM, including generic map-load/template paths. Imports may retain missing/private UUIDs as placeholders without delivery rights. Undo/redo restores only server-owned map frames; HP, initiative and token movement remain outside history.

Migration 006 relaxes map-document version checks to 1/2 and adds encounter/template scenery asset reference tables. Encounter references retain assets needed by current documents and bounded undo/redo frames; only current visible placements grant players binary retrieval. Templates hold independent references and never grant player access. Reference synchronisation locks all affected asset rows in one sorted order, shared with miniature persistence/deletion, to avoid assignment/deletion races. Template save/overwrite/duplicate/rename/delete updates references transactionally. Deletion is blocked for references from combatants, current/history maps or reusable templates. Removing a placement never deletes the file. Historical exports/checkpoints outside retained editor history can restore missing assets as placeholders.

Player snapshots exclude invisible scenery; public snapshots contain no template library/history. File delivery extends the existing endpoint to current visible scenery references, rechecking live membership, active session/encounter, ready owner-matching asset. Hidden-only/history/template/foreign references confer nothing. No GLB bytes travel over Socket.IO. Full changed-map snapshots and existing recovery/reconnection handling preserve player cameras; combat-only updates continue omitting the unchanged map.

## Verification

Unit tests cover v1/v2 compatibility, strict transforms/IDs, mixed serialisation, all edits/history, limits and shared model independence. PostgreSQL/Socket.IO tests cover DM/two-player broadcasts, forbidden/stale/cross-campaign commands and retrieval, hidden/history grants, template isolation/duplication/deletion guards, import/export, reconnect and restart. Browser tests cover the picker, preview, snap/free placement, selection/transforms/duplication/removal, cancellation, history, repeated shared assets and camera preservation. Run all existing unit/integration/browser tests, lint, type checks and production builds. Document practical cache limits and profile real Meshy assets separately.

## Delivered modules

`shared/scenery.ts` contains shared bounds, positions and the asset-prop variant; `shared/dungeon.ts` integrates v2 validation and editing into the existing collection/history. `server/scenery.ts` synchronises current/history/template references, with `miniatures.ts` taking one sorted union of relevant asset locks. `game.ts`, `maps.ts` and `assets.ts` use those references for persistence, deletion guards and scoped delivery. Migration 006 is additive apart from broadening document-version checks. `SharedModel3D` is the common miniature/scenery renderer; `Scenery3D` supplies map coordinates and editor hits, while `modelResources.ts` owns cloned ghost materials. `DungeonBuilder`, `DungeonScene` and `SceneryProperties` integrate the existing library picker, floor raycasts, keyboard cancellation and authoritative property edits. No generator algorithm changes or dependencies were needed. See the runbook for completed verification and limits.
