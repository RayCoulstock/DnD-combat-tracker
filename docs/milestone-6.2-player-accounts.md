# Milestone 6.2 — player accounts and reliable return

## Phase 0 findings (12 November 2026)

Audited main `5814b24`, `server/app.ts`, `server/sessions.ts`, `server/game.ts`, migrations 001–013, `src/Multiplayer.tsx`, `src/sessionBootstrap.ts`, existing PostgreSQL/Socket.IO/browser tests, multiplayer architecture/development and session-start synchronization reports, and canonical UI guidelines/matrix. No production connection or data was used.

Current credentials live in `users` (normalized email, Argon2id, UUID); Passport local authenticates accounts as DM identities. `memberships` are separate stable UUIDs with display name, campaign and revocation, but no account association. Invitations are 32 random bytes, SHA-256 at rest, 30-minute expiry and single-use/revocable, redeemed under a row lock. They establish a player session whose Actor ID is the membership ID. Combatant owners reference that membership UUID. Express sessions use the PostgreSQL store, hashed SID, signed HttpOnly/SameSite cookie, production Secure, seven-day lifetime, Origin/CSRF protection and session rotation on authentication. Ending play changes `session_active`, not membership or authentication.

Reproduction: `server/tests/player-return.test.ts` passes against the pre-change implementation in an isolated schema. A player joins session one, is assigned a character, disconnects after session end, and successfully receives a different authoritative map in session two using the same cookie. Expiring only the player's server-side login makes `/api/session` return null and protected snapshot return 401; membership remains unrevoked and character ownership remains unchanged. The used invitation is rejected. A replacement invitation creates another member ID and restores access, while the original character remains owned by the original member. This reproduces a credible explanation for the reported reinvitation repair, not proof of the historical production incident. No production timestamps/cookies/logs were supplied. Valid-session encounter switching was not broken in this reproduction.

The previous session-start fix already subscribes waiting players before authoritative read, emits revisioned `session.state`, retains waiting subscriptions, and orders encounter changes by campaign state_revision. These mechanisms must be retained. Additional risks found: the browser describes all socket revocation/expiry as needing reinvitation, retries authentication failures indefinitely, and has a stale HTTP error path capable of clearing a newly selected context. These need explicit C handling, not an assumption that registration repairs synchronization.

## Proposed increments and boundaries

A: additive shared-account display name and nullable membership account association with unique (campaign, account); keep membership/owner IDs and existing legacy sessions. Register only with a locked valid invitation or an authenticated legacy claim. Existing accounts accept invitations/claims transactionally; reject conflicting associations rather than merge by name/email. Resolve campaign-scoped Actor at HTTP/media/socket boundaries, preserving existing domain player IDs and ownership gates. Account authentication is independent of campaign role: one account may own one campaign and participate in another. Keep the private-beta DM bootstrap registration flag; production public registration remains closed.

B: My Campaigns uses authorized membership/ownership queries, exposes host display name/status without other members' emails, and provides role-aware campaign entry. Extend DM setup for targeted legacy-claim invitations, status and confirmed revocation. Revocation must invalidate only that campaign subscription, not unrelated account sessions/memberships.

C: retain the existing revisioned stream; cancel/ignore stale context requests and socket callbacks, distinguish authentication expiry from membership revocation, give finite/manual retry for authentication failures and useful map/session loading/waiting errors. Cover two sessions, expiry/login, REST/socket races, multiple campaigns/tabs, reconnect/restart and authorized fog/lighting/map recovery.

No outbound transactional mail adapter/configuration exists in the repository. Password recovery remains disabled and must not be labelled delivered or replaced with emailed passwords, public reset links, password hints or token logging. Enabling recovery requires an approved delivery adapter, hashed expiring single-use tokens, rate limits, session invalidation and actual delivery tests. Operators must use established authenticated administration and identity verification for account incidents; no unauthenticated recovery bypass is introduced.

## Migration, rollout and rollback risks

Use only additive migration 014, nullable account association and defaults; no deletion/recreation of members or owner references. Back up PostgreSQL and private assets with the existing manual deployment procedures; rehearse on a restored isolated staging database first. No production writes or automated deployment. The old binary can read the additive schema and legacy sessions, but cannot log linked accounts into player memberships and may treat account authentication as DM-only; rollback is therefore a coordinated frontend/backend rollback, preserving the new tables/columns and backups, not a destructive down migration. Do not clear member IDs, combatant owners, sessions, maps or invitations. Restoring a backup loses subsequent writes and requires explicit operator approval.

Test plan: preserve the Phase 0 legacy two-session reproduction; add transactional invitation replay/expiry/revocation/concurrency, duplicate email/rollback, account login/logout/session expiry, safe legacy claiming and ID/ownership conservation, cross-campaign/media/domain authorization, revocation/socket isolation, migration from existing data, fresh/returning browser flows and campaign/session race coverage. Run lint, frontend/backend types, unit, PostgreSQL integration, relevant browser suites and production build per increment. Actual staging/private-map/physical-device acceptance remains separate and must be reported honestly.

## 6.2A implementation

`014_player_accounts.sql` adds users.display_name / disabled_at, memberships.account_id and a partial unique (campaign_id, account_id) index, plus an optional invitations.membership_id for DM-authorized claims. Old rows receive defaults/null associations. IDs, passwords, foreign keys to members, invitation hashes, ownership, map/session/encounter JSON and previous migrations are not rewritten. New account IDs never replace combatant owner IDs.

`server/accounts.ts` reuses Argon2id/password policy, the existing cookie/session store, CSRF/Origin middleware and the existing authentication rate limiter (30 attempts / 15 minutes). Invitation inspection/issuance uses a separate bounded 60 requests / 15 minutes limit so validation reads do not exhaust the login budget. Passport uses the same account verifier (including dummy hash for unknown users). New registration requires either a valid invitation or current legacy-session proof. Accepting/claiming locks the campaign then invitation/member, links in one transaction, and only consumes the invitation after successful writes. Duplicate email, replay, expired/revoked tokens, wrong-campaign targets, conflicting existing memberships and simultaneous redemption roll back safely. Display names and matching emails never establish claim authorization. Claimed memberships retain their original display name and all owner references; other legacy credentials for that member are retired. Revoked memberships cannot be silently reactivated by an ordinary invitation.

Credential sessions hold the account identity; HTTP campaign/media requests and every socket command/read resolve the campaign-specific Actor. An owner resolves to DM, a member resolves to the stable member UUID. Player projection, private media checks, character ownership and domain authorization are retained; merely being a user does not grant access to somebody else's campaign. The existing account model permits owning another campaign without a global player/DM role column. Context selection never grants authorization. Portrait grants also resolve linked memberships and retain player projection; missing/foreign GLB and floor-image grants retain the existing indistinguishable 404 behavior. Presence uses the resolved member identity.

New endpoints: POST `/auth/player-register`, `/invitations/inspect`, `/invitations/accept`, `/accounts/claim` and `/campaigns/:id/enter` under `/api`. Inspection uses a body rather than raw tokens in access-log URLs. Existing development/operator-enabled DM bootstrap registration stays behind ALLOW_DM_REGISTRATION; production stays false. Existing legacy invitation redemption is retained during rollout and explicitly labelled browser-only, not permanent identity. Targeted claim links are generated by the authorized DM through the existing invitation endpoint with membershipId; B adds its management control. Claim links cannot be redeemed as anonymous replacement memberships.

A4 Account exposes legacy linking in the existing Modal, preserving the mounted camera. Existing sign-in and invitation entry uses the shared shell and accessible form controls, username/new-password/current-password autocomplete, explicit recovery-disabled copy and touch-size inputs. A signed-in account accepts another invitation directly; expired linked-account credentials can sign in normally without another invitation. B adds My Campaigns and C adds differentiated connection/recovery states.

Recovery is **disabled**, not completed: no transactional email delivery or tested administrator password-reset tool exists. A campaign DM is not granted authority to reset another person's password. Administrators should verify identity through an established trusted channel and use a separately reviewed recovery operation; never delete/recreate memberships, remove owner IDs, email a password or publish a reset token as a workaround. A future recovery operation must retain account/member IDs, validate a new Argon2id hash and invalidate all affected account sessions. Actual outbound delivery testing is a release prerequisite for enabling self-service recovery.

A manual acceptance: invite → create player account → see the authorized map; sign out, reopen the normal bookmark and sign in → same campaign/member/character. For legacy migration, assign a character, use Account → Link player account (or a DM-targeted claim link after legacy expiry), and verify the original member UUID and ownership. Try a different existing membership in the same campaign: conflict must leave both records untouched. Expire authentication in staging, sign in again and verify fog, lighting and map state. Keep another campaign/tab open and check independent authorization. Rehearse the additive migration on a restored staging copy, including existing DM login and legacy cookies. No staging or production deployment has been performed here.

A validation: lint, frontend/backend type checks, production build and unit suite pass (174 passed, three existing platform skips; existing bundle warning unchanged). Full isolated PostgreSQL integration: 109 passed, including the populated migration rehearsal. Final account/claim/tab tests pass after the last proof-gate change. Seven distinct browser scenarios pass across the verification runs: invited registration/normal return, legacy linking with camera retention, closed-registration UI and all four multiplayer scenarios. A software-WebGL camera-settling check passed when rerun without concurrent integration load; its assertions/time budget were not weakened. The invitation UI-contract test now stubs valid inspection metadata rather than pretending a fake token was authorized. Actual staging deployment and outbound email delivery remain unperformed.

## 6.2B proposed architecture

Build on reviewed A's account/member association, not a second membership table. My Campaigns queries the union of owned campaigns and active linked memberships, with role, host display name and current live/waiting flag; never another player's email. A3/A4 navigation opens the C2 dashboard under the existing B bar. Join/Wait uses the existing authorized campaign entry and socket stream, and switching clears the old encounter before loading the new one. DM setup remains the owner of member status, invitation history, confirmed revoke and targeted legacy-claim issuance. Owner details may include revoked members for history, while presence/assignment lists retain active members only. Revoking a linked member keeps account credentials and unrelated campaign sockets, but invalidates the affected subscription and outstanding targeted claims. No schema beyond A is necessary.

## 6.2B implementation and review

My Campaigns uses the existing authenticated `/api/campaigns` query and authorized `/enter` endpoint. Account credentials can resolve different member IDs in different campaigns and host privileges only in owned campaigns. Cards show campaign/host display name, active membership or host role, Live/Waiting and Join/Wait/Open actions; a normal account login opens the dashboard. Invitation entry can still take the player straight into the campaign. Host creation remains possible without a rigid global player role. A3 navigation and the A4 Account menu reach the C2 dashboard (including phone), below the existing B context bar. Opening it hides/inerts the retained map; choosing another campaign clears old state before entry. The selected room's existing session stream updates its card; Refresh campaigns refreshes other cards without background polling.

DM setup now shows linked/legacy/revoked membership status and a targeted Claim link action, retaining the existing Online/Offline indicators, invitation history and confirmed Revoke button. It merges current presence with owner metadata, refreshes metadata on opening setup, and offers Refresh members for changes made elsewhere. Assignment lists stay active-only, with an existing revoked owner shown as a disabled option rather than silently reassigned. Revocation preserves the member row/owner IDs, retains the first revocation timestamp, revokes unused targeted claims and immediately invalidates affected API/socket access. Account sessions and other campaign memberships/subscriptions survive. No schema beyond A or separate synchronization path was added.

Browser verification exposed same-document invitation navigation: a second `#invite` link did not remount React, so the old initial-only parser ignored it. A hashchange handler now opens the validated invitation without a page reload. Account linking disconnects the old socket before credential rotation and suppresses expiry recovery while authentication is in progress; failed linking may reconnect the old credential. This prevents legacy expiry notifications from clearing a newly linked view. C extends this with full stale-request/reconnect protection.

Manual B acceptance: sign into an account with two campaigns; open My Campaigns, verify both hosts/roles and Live/Waiting actions, join each and confirm no prior encounter is shown. Repeat on phone/tablet and through A4 using keyboard. Open a second invitation in the same tab, accept it and verify the same account has a separate membership. In DM setup refresh member status, issue a legacy-targeted claim, redeem it and check the same member ID/character. Cancel revoke first, then confirm it: the affected campaign must reject API/socket rejoin while another campaign/tab and the account remain valid. Check that only the owner sees revoked membership history/claim targets and that other players receive no email addresses. Synthetic UI captures: [phone](ui/milestone-6.2/my-campaigns-phone.png), [tablet](ui/milestone-6.2/my-campaigns-tablet.png); no invitation tokens or private data appear in these captures.

B rollback uses matching A frontend/backend binaries and keeps migration 014/data; no down migration. The owner-details API now includes revoked-status rows, so mixed old/new UI deployment is discouraged even though server permission checks remain authoritative.
