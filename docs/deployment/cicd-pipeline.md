# GitHub Actions release pipeline

PR 3 prepares automation; it does **not** provision, configure GitHub settings, publish from this workstation, change DNS or deploy. Staging and production start disabled and must remain so until separately approved infrastructure and recovery evidence exist. Existing standalone development Compose and Windows scripts are unchanged.

## Validation and artifact identity

`ci.yml` runs on pull requests targeting main and is reusable by `publish.yml`. Ubuntu 24.04 hosted runners use Node **24.19.0**, Docker Engine **28.4.0** (pinned setup action), Buildx **0.31.0**, Compose **2.40.3**, Restic **0.18.0**, actionlint **1.7.7**, ShellCheck **0.10.0**, Syft **1.23.1**, and verification CLI **gh 2.74.2**. Third-party actions are pinned to immutable commits with version comments. Binary downloads have committed SHA-256 checks, use HTTPS and fail on mismatches. Chromium and its OS dependencies come from `npx playwright install --with-deps chromium`, matching the committed npm lockfile's Playwright revision; no arbitrary system Chrome fallback exists in CI. Hosted Ubuntu's base OS packages remain runner-managed; tool updates need a reviewed pin/checksum change, not an unbounded upgrade.

The required native job runs clean install, types, ESLint, all unit tests, production compilation, required infrastructure tests, API integration and all Playwright tests. It creates **its own** PostgreSQL 17 container, random credentials, fresh database and private temporary GLB directory; ignores inherited DATABASE_URL; binds the database only to loopback on a random port; and stops its test DB afterward. It refuses occupied app/frontend ports, starts Vite in strict-port mode and confirms its own child servers remain alive before browser tests, preventing an existing local application from being used accidentally. No staging/production credentials are available. Reviewed Caddy/PostgreSQL fixture digests are pinned in CI independently of the production defaults. Failure to fetch tools, Chromium, Caddy or Docker is a failed check, never a skipped release gate.

The dependent image job builds the **repository Dockerfile** via Buildx, Linux amd64, lockfile `npm ci`, no credential build arguments and no weakened TLS/integrity checks. It loads that actual production image, rejects diagnostic labels, verifies non-root UID, compiled frontend/backend/migrations/GLB worker and absence of development tools, then runs PR 2's `backup-recovery-smoke.sh`. This checks real private-CA Caddy HTTPS, cookies, CSRF/Origin, DM/player authorised WebSockets, private GLB uploads, restart, persisted encounter/model data, matched encrypted Restic backup, wrong-password denial and restoration into fresh storage. This local synthetic rehearsal is not a DigitalOcean or off-server Spaces test.

Only **after success** does it save the tested Docker image, image-ID/commit evidence, SBOM and checksums as a one-day Actions artifact. This is an application-image artifact, not a runtime snapshot. No private GLBs, database dumps, cookies, env files, test screenshots or Playwright traces are uploaded. Three-day failure artifacts contain safe status/count summaries (Buildx build records also have three-day retention); console output and Buildx's build report provide build diagnostics without production secrets. Filesystem fixtures remain only on the disposable runner. Do not enable arbitrary debug env/config dumps or upload `/tmp`, test-results, Docker inspect/config output or restored files.

## Main publication and GHCR

`publish.yml` triggers **only push to main**. Main must already be protected by the owner; publication fails if GitHub does not report a protected ref. No `pull_request_target`, workflow-run privilege bridge, fork publication, inherited secrets or PAT is used. The full reusable CI runs again on that exact main commit; branch PR validation alone is insufficient. Only its dependent publication job receives `packages: write`, `attestations: write` and `id-token: write` alongside contents read. Use the repository `GITHUB_TOKEN` for GHCR login.

Image name: **`ghcr.io/raycoulstock/dnd-combat-tracker:sha-FULL_COMMIT_SHA`**. Release selection always uses **`ghcr.io/raycoulstock/dnd-combat-tracker@sha256:…`**, never a moving tag. There is no latest tag. The publisher downloads the same run's immutable Actions artifact, verifies SHA-256/evidence/image ID/revision, loads and pushes it **without a rebuild**, pulls the resulting digest and compares its image ID to the tested artifact. Docker transport can change layer compression, but the tested image configuration and uncompressed filesystem identity must remain identical.

GitHub artifact attestations bind provenance and SPDX SBOM to the published digest and protected main workflow. Local `--load` cannot retain a BuildKit attestation index; these are **post-test GitHub workflow provenance/SBOM attestations**, not a claim of a retained BuildKit build attestation. Labels associate source/revision with the repository. No job is successful until push, identity check, attestations and release-report upload all succeed. A partially pushed image after a later failure is **not approved**: deployment requires the successful publication run and attestation, not mere registry presence.

The 30-day `release-FULL_SHA` artifact records commit, Docker image ID, GHCR digest, validation flags and workflow run ID; summary and SBOM contain no runtime data. Record approved digests/reports in the release/change record. After evidence expiry, this workflow refuses promotion; validate/re-publish a reviewed main release rather than bypass evidence checks. Commit tags aid discovery, but mutable tags never establish trust.

Owner must configure GHCR package visibility deliberately (new packages are normally private), link it to this repository and grant this repository's Actions access. Keep private if models/source policy requires it; the image excludes all uploaded models. The publishing GITHUB_TOKEN suffices; do not create a broad PAT. Runners use read-only package access for promotion verification. An external private-GHCR Droplet needs **independent scoped read-only pull/authentication** (for example a dedicated machine credential/credential helper); a job's short-lived publication token is not a permanent host secret. Host GitHub release/attestation verification also needs read-only repository Actions/attestation access for a private repository. Never grant the host package write permission.

## Owner settings required before use

1. Enable Actions with an allowlist covering the pinned actions; allow read-only default workflow permissions, with explicit job grants as committed. Ensure artifact attestations/GHCR are supported by the repository plan and policy. If APIs/features are unavailable, promotion must stay blocked; do not silently drop checks.
2. Protect main with a ruleset/branch protection: require pull requests, review (including workflow/ops changes), dismiss stale reviews, prevent force pushes/deletion and bypass, and require current checks. Select **`Required tests`** and **`Production image and recovery`** from the actual CI run's check names (GitHub may prefix reusable jobs with `validate /`). Do not require the main-only publish job as a pre-merge PR check. Restrict direct pushes; do not permit unreviewed main publication. Consider CODEOWNERS for `.github/`, `Dockerfile`, `deploy/` and `scripts/ops/`/`scripts/ci/`.
3. Create GitHub Environments **staging** and **production**, with independent secrets and targets. Each requires at least one reviewer, **prevent self-review**, **disable administrator bypass**, and **Selected branches and tags: branch main only** (no main tag, wildcard or other policy). The workflow verifies required reviewers, self-review prevention and branch policies at runtime and refuses absent/ambiguous policies. The REST GET-environment API does not expose the administrator-bypass setting: the owner must verify it is disabled in Settings before setting DEPLOY_ENABLED; runtime refuses it if a future API explicitly reports it enabled. This manual policy check is not claimed as API-verified. A missing Environment must not be created as an unprotected substitute. Required reviewer support can depend on repository visibility/plan; upgrade/resolve access, keep disabled otherwise.
4. Keep environment variable **DEPLOY_ENABLED absent/false** until its own infrastructure, scoped credentials, target identity, public TLS and real backup/restore prerequisites have been separately approved. No automatic push/release deployment trigger exists.

Environment variable names: **DEPLOY_ENABLED, SSH_HOST, SSH_USER, SSH_PORT, TARGET_ID**. Environment secret names: **SSH_PRIVATE_KEY, SSH_KNOWN_HOSTS**. Values are not provided here. Pin a separately verified SSH host key, including `[host]:port` notation when needed; never discover/trust the key automatically in CI. Use different staging/production keys and identities, and a dedicated restricted account/forced-command key. No database, session or backup secrets go into GitHub build jobs or image build arguments.

## Preparing a future existing host

This is an **upgrade** pipeline, not first installation. Approve/provision/harden the server and initialise its first database manually under the PR 2 guide in a separate phase; no empty-backup/first-install exception is automated here. Staging must have separate Droplet/hostname, database, volumes, secrets, backup repository/project and SSH keys. Do not point it at production storage. Never enable staging as an alias for the production host.

After review, install `scripts/ci/deploy-host.py` as root-owned, non-writable-to-deployer **`/usr/local/sbin/ledger-release`**. Install the reviewed `scripts/ci/ssh-release-command.py` as root-owned `/usr/local/sbin/ledger-ssh-command`. Restrict the environment-specific authorised key with `restrict,command="/usr/local/sbin/ledger-ssh-command production TARGET_ID"` (or staging and its different target). The wrapper validates the exact original command and binds that key to its own environment/target without shell evaluation; `restrict` disables forwarding, PTY, X11 and user rc. Normal shells/file transfers must not be available to that key. Docker-group membership remains root-equivalent; wrappers do not replace host administrator controls.

Install a **root-owned infrastructure checkout** at `/opt/encounter-ledger/infrastructure` pinned to a reviewed commit, readable but not writable by the deployment account (including all parents, files and Git metadata). Do not install npm dependencies in it. No automatic git pull/reset runs on the host. Configure Git's safe.directory deliberately for operator inspection; the driver scopes that setting to its own read-only invocation. When infrastructure changes, an administrator reviews and updates this checkout and the configured infrastructure commit independently of selecting an older compatible application image.

Copy `deploy/release-host.example.json` to `/etc/encounter-ledger-releases/production.json` or `staging.json`, in a separate root-owned 0755 directory, root-owned and not writable by deployer; keep **enabled false** initially. It must not reside in the operator-writable runtime-secrets directory. Configure environment/project, independently verified `/etc/machine-id`, unique target ID (same as Environment TARGET_ID), exact public origin, approved infrastructure commit/image repository, reviewed disk headroom (at least 10 GiB free for Docker and backup staging) and timestamp of a **successful real off-server restore rehearsal within 30 days**. This timestamp is operator-attested evidence, not an automated Spaces test. Provision directories, runtime/backup secrets, lock permissions, Docker/Compose, Python, Restic and pinned gh CLI per the PR 2 guide. Never pass a fake restore timestamp to make the pipeline green.

Operator-owned **0600** host files (outside Git): `/etc/encounter-ledger/production.env`, `production-backup.env`, `production-check.json`, or corresponding staging files. Runtime and backup fields remain those in PR 2 examples. The check JSON fields are **origin, email, password, playerCookie, campaignId**: manually provision a dedicated synthetic DM and authorised player session in a non-game verification campaign with an active encounter. Its player cookie expires/revokes normally; renew it securely before a release when needed. Never reset a real DM password or issue/refresh invitations automatically to make a deployment pass. The live check only logs in, reads state, joins authorised sockets and logs the synthetic DM out; it never moves tokens, edits maps or creates accounts. Secrets travel to the disposable verification container through stdin, not CLI arguments/environment/layers. It uses normal public HTTPS validation, not an insecure/private-CA production override.

The driver is restricted to an existing healthy app/PostgreSQL/Caddy installation, fixed production/staging project identity, expected host machine ID, approved root-owned infrastructure, exact origin, disk headroom and reviewed recent restore. It independently rechecks the successful main publication and exact image attestation using host read-only GitHub access. It holds the **same per-project maintenance lock** across backup, migration, startup and verification; backup/migration children validate the inherited descriptor and lock, and scheduled maintenance is excluded throughout.

## Approved promotion and failure handling

After separately approving a release window and environment, manually dispatch the desired environment workflow **from main**, supplying a successful main **release_run_id** and its exact **digest**. GitHub requires the environment reviewer before secrets/SSH. The runner verifies enablement, reviewers/branch restrictions, run repository/workflow/event/conclusion/commit, release artifact/digest and GitHub attestation. It then uses only the pinned SSH key/host key and a fixed validated remote command.

Host sequence: verify target/config/health/capacity and approved registry image → pull/verify digest and commit → **matched encrypted backup with `--keep-stopped`** → retain successful snapshot ID → atomically set the private runtime LEDGER_IMAGE → explicit approved migration → start app/Caddy with readiness → independent public HTTPS/frontend/Secure-cookie DM/player/authenticated-WebSocket check → safe workflow/host report. App and PostgreSQL ports remain private. Private runtime Compose is parsed internally and never printed. The pipeline does not change DNS, firewall, TLS trust, proxy config, infrastructure checkout or volume identity.

Before writes stop, a failed gate/pull leaves the current app alone. From backup onwards, failures **leave app writes stopped**, including failed live verification after startup. No automated image rollback, database restore, down migration, seed, volume prune or reset occurs. An operator inspects the recorded snapshot, SQL state and image compatibility and chooses recovery. A hard runner/SSH/host failure can interrupt reporting; inspect host/container state before retrying. Monitoring must alert on unavailable readiness, failed releases, backup age, disk, certificates and OOM/restarts; a GitHub green job is not ongoing monitoring.

A previous image may be promoted only if it has successful unexpired publication evidence/attestation and the owner confirms compatibility with the **current schema**. The same backup/migration/approval gates apply. If SQL compatibility is uncertain, restore the matched DB/GLBs into a separate environment under PR 2's procedure and verify before an approved cutover; never assume changing a tag reverses a migration. Expired evidence or unavailable GitHub services blocks deployment rather than accepting an arbitrary older image.

## Investigating failures and next phase

Read the failed named check and safe summary first. A build registry DNS/TLS/integrity failure must be fixed at the builder/network/CA source; do not substitute native dist files, skip smoke, disable TLS or enable diagnostic production images. Chromium/tool download failures are infrastructure failures, not successful tests. Review Buildx's no-secret build record; reproduce with the same commit/pins. Never upload private runtime directories to investigate.

For promotion failures check environment plan/permissions, reviewer rules, main protection, artifact age, publication conclusion/digest, attestation identity, strict host key, target marker, root-owned checkout, storage health and off-server repository availability. Inspect protected host diagnostics without dumping config. GHCR images may exist after a failed publication; only a successful release run authorises them. No GitHub-hosted run, GHCR push, environment approval, real SSH deployment, DigitalOcean/public ACME or off-server verification is claimed by local validation.

PR 4 should configure and exercise repository protections/CI/GHCR first, then separately provision an approved staging environment and demonstrate real restore, scoped SSH, gated deployment/failure recovery, capacity and alerts. Resolve open DM registration/storage quotas before public access. Production's first installation and subsequent approval remain separate human decisions.
