# Repository audit — production readiness, PR 1

Audited 26 October 2026, against the completed map-editor workspace (now merged into `main`). This is a repository-only review and local validation. No VPS, DNS, cloud firewall, certificate or production deployment was created or changed. Existing databases and uploaded assets were not reset or removed. Tests use a separate PostgreSQL 17 container and fresh temporary asset directories.

## Findings and changes

| Area | Finding | Resolution / recommendation |
| --- | --- | --- |
| Build | Shell `cp -r` fails on Windows; TypeScript does not copy SQL. | Node filesystem copy script resolves from its own module location, copies SQL byte-for-byte, replaces stale compiled SQL, and rejects an empty source. A test includes paths with spaces and repeated builds. Native Windows execution still needs Windows CI. |
| Runtime dependencies | Vite, its React plugin and TypeScript were production dependencies despite only being build tools. | Moved them to devDependencies and refreshed the lockfile. Runtime still uses `npm ci --omit=dev`; the frontend is served as built static files. Client libraries remain classified as production dependencies; trimming those is optional image-size work. |
| Image | Existing Node 24 Debian slim multi-stage build, non-root `node`, separate npm install, compiled worker and persistent asset volume were sound. No readiness probe or explicit stop signal. | Retained the design, added a Node-based readiness health check and SIGTERM stop signal. Runtime contains `dist`, `dist-server`, SQL and production dependencies. No migration or seed runs automatically when starting the image. |
| Migration | Transactional, sorted SQL with an advisory lock; startup previously checked only that `schema_migrations` existed. | Startup now requires all shipped SQL names to be applied. Migration CLI fails without DATABASE_URL and reports failures without raw connection errors. No new schema migration in this PR. Existing seven migrations remain unchanged. |
| Seed | Explicit credentials and Argon2id, no default DM password, but production execution was not guarded. | Development seed now refuses NODE_ENV=production before accessing the database. Production account creation remains through the existing registration UI. |
| Database | Pool max 10, transactions release clients, but connection acquisition had no deadline and idle-client errors had no listener. | Added 5-second acquisition/connect timeout, 30-second idle eviction, and a generic idle error handler. Health query has a 3-second read timeout. Database reconnection is demand-driven by pg, not a new retry loop. |
| Configuration | Application validated the session secret and origin; entry point did not validate DB URL, port or storage before connecting. | Central runtime preflight validates these keys without echoing supplied values. Absolute private storage is required in production. New `.env.production.example` documents all supported limits and proxy settings. |
| HTTPS proxy | Secure/HttpOnly/SameSite=Lax cookies, exact HTTP/WebSocket origins and CSRF already enforced; one proxy hop was hardcoded. | TRUST_PROXY supports `1`, `loopback`, `0`; production retains the one-hop default. A production-mode integration test verifies Secure cookie registration behind a trusted HTTPS proxy and rejects forged forwarding without trust. **Port 3001 must be private** with exactly one Caddy hop when using `1`; this is not a safe setting for a public Node endpoint. |
| Socket.IO | WebSocket-only, authenticated session and CSRF handshake, authorised campaign subscriptions, ordered revisions and reconnect snapshots. | No protocol changes. Caddy must preserve Origin and support upgrades. The same origin serves frontend/API/socket; no wildcard CORS or camera synchronisation is introduced. |
| Health | `/api/health` queried PostgreSQL but returned a generic 500 on outage. | Anonymous readiness now returns 200/503 with only `{ok:true/false}`. `/api/health/live` reports process liveness without a database query. Neither proves backups, available disk capacity or every asset file. Docker marks unhealthy but does not itself restart an unhealthy process. |
| Shutdown | Existing Socket.IO/HTTP close and pool drain had no duplicate-signal guard or deadline. | Entrypoint accepts SIGTERM/SIGINT once, closes the application and pool, and enforces a 30-second maximum. Future Compose should use `init: true` and stop_grace_period of at least 35 seconds. |
| GLB storage | Streaming capped uploads; self-contained GLB validation in heap/time-limited workers; private authenticated delivery, hashed server-controlled filenames, no path traversal. | Keep filesystem storage outside `/app`, mounted persistently with UID/GID 1000 ownership. Do not publish it as a Caddy static root. The compiled worker remains shipped and is part of runtime validation. |
| Recovery | Startup reconciles pending file publications, missing pending records, old staging files and tombstoned deletions. | Existing behaviour preserved. Restore DB and asset files together **before** starting the app. Recovery cannot reconstruct missing ready GLBs or infer ownership from orphaned files. It is not a backup strategy. |
| Secret boundary | Frontend uses relative API/socket URLs; Vite exposes VITE_-prefixed build configuration. Existing `.dockerignore` excluded env files but not arbitrary GLBs/logs/key files. | Added GLB, private-key, certificate, log and coverage exclusions. Production env example is tracked but excluded from Docker context by `.env.*`. Never use VITE_ for secrets, COPY env files, or pass credentials as ordinary build args. Optional existing build_ca is a BuildKit secret mount. |
| Local Compose | PostgreSQL 17 volume and loopback binding; optional app profile uses development DB password fallback and HTTPS localhost placeholder. | Preserve for local development. **Not production Compose**. PR 2 must require credentials, omit public app/DB ports, add Caddy persistent state, readiness ordering, migration release step and backup/recovery operations. Never use `down -v` on a live installation. |
| Tests | Domain, API security/persistence and multi-browser regressions already present; no established GitHub Actions workflow. | Preserve all game tests. Added build-copy, runtime preflight, missing-migration, health-outage, seed/migration guard and production proxy tests. PR 2 should gate images/deployment on these suites, not bypass them. |

## Remaining risks before public deployment

1. Full Docker build and image smoke must pass on a builder with npm registry access. This environment's Docker RUN networking repeatedly fails with `EAI_AGAIN` for registry.npmjs.org, including host-network and proxy/CA attempts. Native builds are not evidence that a full image was built. See the validation record in the readiness guide.
2. Public DM self-registration remains enabled, as in the existing app. There are no account disk quotas or email verification; rate limits do not replace an admission policy or disk limits. Decide the intended DM registration policy before unrestricted exposure. No authentication redesign was made here.
3. No real Caddy TLS, DigitalOcean firewall, external DNS, remote DB certificate chain, internet latency or power-loss restore has been exercised. The trusted-forwarding test simulates the proxy locally.
4. Backups, off-host retention, restoration rehearsal, disk/inode monitoring, log rotation and session/receipt retention need operations work. Expired sessions are denied but currently not periodically purged. No data retention/deletion job was added.
5. GLB workers can use two 256 MiB JS heaps plus model buffers/native memory. Set VPS/container resources based on actual uploaded models and concurrent validation; budget PostgreSQL and browser workload separately. Large frontend bundle advisory remains; no load/performance claim is made.
6. Base images use maintained Node 24 / PostgreSQL 17 tags rather than immutable digests. PR 2 should establish image pinning/update/scanning policy and release rollback by application image digest. A database migration is not automatically reversible by rolling back the app image.
7. Filesystem/DB publication is coordinated by recovery, not one cross-resource transaction. Preserve matched backups and test upload/restart failures. Do not scale app replicas over this filesystem design.

## PR 2 recommendation

Provision one Ubuntu VPS with non-root administration and key-only SSH; expose only restricted SSH plus Caddy HTTP/HTTPS. Use a private Compose network for Caddy → app:3001 → postgres:5432, named persistent volumes for PostgreSQL, GLBs and Caddy state, explicit secrets at runtime, health ordering and a one-shot migration release job. Back up and restore-test DB + GLBs before first release. Add GitHub Actions validation/image publication first, then a separately approved deployment job with scoped credentials, pinned SSH host keys and a manual production environment gate. Do not introduce Redis, Kubernetes or horizontal scaling for this topology.
