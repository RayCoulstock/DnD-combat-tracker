# Milestone 6.0 — atmospheric lighting

## Audit and architecture, before implementation

Main commit 07f055d includes Milestone 5.7.1 (terrain/inspector) and c18dff6 (CI selection/readiness repair). The working tree was clean. Repository merge state is verified; this task does not independently verify or change production deployment.

BattleMap3D owns one R3F Canvas with demand rendering, ACES filmic tone mapping (R3F default), sRGB output and shadows. Its ambient light is white/intensity 1.05; its directional light is at [8,14,6], intensity 2.1, 1024px shadows. GLBs use shared cached/cloned models and lit standard materials. Calibrated images, repeating textures and terrain masks use unlit basic materials to preserve artwork; procedural geometry uses standard materials. Floors share one scene with elevation groups and optional stacked visibility. Map commands, bounded history, server transactions/revisions, player projection and JSON/template persistence already support optional appearance data.

### Three reviewable increments

- **6.0A** adds optional global lighting.environment and per-level lightingOverride, legacy-compatible rendering, environmental controls and local Low/Medium/High quality/flicker preferences. Enabling atmospheric lighting opts floor artwork into a consistent lit material, with a small legibility fill; maps with no lighting fields keep their original materials/lights/exposure. No GLB binary or cached material is changed.
- **6.0B** extends the same map-owned rig with stable point emitters, existing-grid placement, gizmos, explicit local attachments, safe detach/missing-parent behavior, optional bounded shadows and subtle local flicker. Reuse existing object/combatant updates, not animation-frame commands.
- **6.0C** adds map-scoped snapshots of environmental/floor overrides and existing emitter appearance, explicit scene CRUD/activation/previous restoration and authoritative transition metadata. Saved scenes never copy geometry or GLB binaries; normal edits do not autosave them.

Use additive JSON normalization, no separate renderer/service/store and no SQL migration. Existing records are not rewritten. Older strict map readers will not accept new fields, so coordinate binary rollback and keep untouched map copies. Each increment gets its own branch/commit and focused tests/documentation; no automatic deployment or 6.1 work.

### Per-floor policy

Three.js ambient/directional lights affect the entire scene. This milestone deliberately implements **active-floor atmosphere**: the viewer's active floor merges selected override properties with the global environment. All simultaneously visible floors share that environment; inactive floors are not independently illuminated. In B, only active-floor emitters contribute. Overrides/emitter data remain floor-associated for future isolated rendering. UI discloses this policy. Floor switching changes the chosen atmosphere without resetting renderer, camera, objects or floor data. Hidden floors remain filtered, and can never become a light-data side channel.

### Material/quality/resource policy

Absent lighting data reproduces the existing white lights, shadow defaults, unlit artwork and exposure. Configured maps use opt-in standard materials for floor images/textures/terrain, retaining UVs, masks, opacity, clipping and tint. A modest emissive/fill component prevents an artistic dark scene from becoming a rules-based black screen; grid and labels retain their visibility. Artist exposure is bounded. Lighting has no effect on HP, ownership, initiative, movement, visibility permissions or campaign state.

Quality is local viewer preference, never authoritative map data. Low: four point lights, no shadows/flicker; Medium: eight, one selected point shadow; High: sixteen, two selected point shadows. Directional resolutions are capped by profile/GPU limits; point shadows use smaller bounded maps. No automatic FPS claims. Reduced motion disables flicker and transition animation. Shadow targets are disposed on replacement/disable/unmount; demand invalidation runs only while a permitted animation is active. Existing Asset Library previews retain their own lights.

### Attachments, scene privacy and transitions

B attachments reference stable scenery/combatant IDs plus explicit local offsets. Resolve grid anchors, rotation, scale/vertical offset and effective floor from existing state. Detach retains resolved world placement; removed parents safely detach at their last committed location. Hidden/unplaced combatant emitters are not projected to players. Standalone gizmos/names and scene management remain DM-only; players receive only permitted effective light data, not private presets/previous snapshots/hidden floor or hidden parent identities.

C captures environmental/floor overrides and existing emitter appearance, not placement or attachment identities. Activating a scene preserves current geometry, combat state, positions, active floor and camera. Missing/deleted light references are skipped, not resurrected. Explicit Save Changes/Save as New records current settings. Activation/restore stamps one server time and transition ID/duration through existing revisions; targets persist immediately. Existing viewers interpolate locally from current appearance; initially joining viewers render the authoritative target, and elapsed transitions snap to final. No per-frame networking or serialized renderer objects.

Risks to test: legacy material parity; opting lit terrain into the same colour/alpha pipeline; active-floor disclosure; light/parent floor transfer and deletion; hidden source/preset projection; bounded point/shadow budgets; stale revisions; transition/reduced-motion behavior; repeated resource replacement and retained scene identity. Physical-device and assistive-technology checks remain manual.

## 6.0A implementation and acceptance

`lighting.environment` is optional document-level data; `lightingOverride` is optional level geometry data. `map.lighting.environment.set` and `map.lighting.override.set` use the existing DM-only map edit/history/revision pipeline. Global data is explicitly excluded from level geometry and retained through composition/duplication. Partial floor overrides copy with their floor and disappear with it; hidden floor records remain excluded from player projection. There is no SQL migration.

The viewer's local quality/flicker keys contain no campaign or map data. Existing maps use legacy white ambient 1.05, directional 2.1 at [8,14,6], exposure 1 and basic floor materials; configured maps use the opt-in material and a small fill. Shader cache keys distinguish clipped images from repeating/masked artwork. Directional shadow maps are bounded/disposed on quality changes, and renderer exposure/shadow settings are scoped/restored imperatively. Asset previews are unchanged.

## 6.0B implementation and acceptance

Optional `lighting.sources` holds at most 32 validated emitters. Each has a stable ID, floor, grid-square position and height in feet, appearance and optional scenery/combatant attachment with local offsets. Offsets rotate with the parent and scale with its appearance; vertical offsets include the miniature base. Source positions retain the last committed resolved fallback. Existing movement/appearance commands update this fallback without animation-frame commands, retain the existing map history and preserve the combat/tactical clock contract. Explicit parent deletion detaches; unavailable imported parents use the fallback for the DM and are withheld from players. Unplaced parents do not emit. Floor duplication remaps scenery parents and emitter IDs, excludes combatant attachments, and validates capacity atomically. Floor deletion removes its sources.

D4 Lighting selects/places/moves sources; a C3 Add at level centre action supports keyboard creation followed by numeric position editing; C3 Editing → Selection provides preset selection, the active-floor list and retained-draft Light Properties. Controls include height, colour, numeric/range intensity/radius, enabled, selected shadows, local attachment offsets, detach, duplicate and confirmed delete. Gizmos exist only in the DM editor. D3 undo/redo uses one frame per committed operation. Player projection filters effective floors/parents and replaces private source names with “Light”.

Only the active floor emits, including stacked view. Stable-ID priority follows enabled lights, then source ID within each local point budget. Selected shadows are bounded by the viewer profile (0/1/2); point maps are 128/256/512px, also capped by GPU atlas limits. Optional point shadows update on rendered frames so newly loaded GLBs do not leave stale placeholder shadows; this costs more than unshadowed lights. They are off by default. Shadow targets are disposed on replacement/unmount. Flicker is smooth, seeded, locally animated, bounded and disabled by reduced motion, Low quality or the local flicker preference. No network writes occur during animation.

Manual B checklist: add a Torch on a floor square; change colour, height, intensity/radius; move, duplicate/delete and undo/redo. Attach to a scaled/rotated GLB and a miniature, move/transfer them, detach and verify world position. Remove a parent and reload. Check hidden/unplaced parents as a player and verify gizmos never appear. Test selected point shadows, local quality and reduced motion; compare repeated edits with the same scene/camera. Existing map, terrain and combat state must remain unchanged. Physical GPU/tablet performance remains a manual check.

B validation: seven focused shared tests, six database/socket tests and the point-light browser workflow passed. Lint, type checks and build passed; existing bundle-size advisory remains. Final cross-feature regression is scheduled after C.

## 6.0C implementation and acceptance

The same optional rig now supports at most 12 map-scoped `scenes` (stable ID, name, description, default duration, snapshot), `activeSceneId`, a private `previous` snapshot/previous scene ID and public `transition` metadata. A snapshot contains environment, partial overrides keyed by floor ID and appearance keyed by source ID; it excludes names, positions, attachment identities and all geometry/combat data. Total lighting JSON is capped at 200KB in shared/server validation to bound history/payload growth. No SQL migration, new dependency or binary asset is required.

DM commands: `map.lighting.scene.save`, `.rename`, `.duplicate`, `.remove`, `.activate`, `.restore`. Save explicitly captures current lighting (including Save as New); rename edits metadata without replacing captured appearance. Activation updates current source appearance only, ignores missing/deleted source/floor references and leaves new uncaptured sources unchanged. Restore swaps the previous snapshot, allowing reversal without changing geometry. Ordinary lighting edits mark the active saved scene dirty rather than overwrite it. Duplicate/delete and activation are undoable through existing map history. Scene names need not be unique; IDs are authoritative. Deleting an active preset keeps the current lighting.

C3 Map → Lighting Scenes provides active/dirty status and an existing native-modal management surface with search, metadata, duration, CRUD, activation and previous restore. No extra session-bar control is needed: scene changes are contextual editor operations. Modal Escape/focus restoration reuse Phase 1. Full-width fields and wrapping actions fit laptop/tablet layouts.

Activation/restore commits the final target plus a UUID transition, bounded duration (0–10 seconds) and server-stamped start time after receipt/revision validation. Existing clients blend from their currently displayed colour/intensity/direction/exposure/radius to the target for the remaining interval. Enabled emitters fade via intensity; shadows/quality flags switch immediately. Floor changes, reduced motion, late initial mounts and elapsed transitions snap to the final target. A new activation can interrupt the current blend. Unrelated movement does not restart animation. Culling a light outside the local point budget can cause it to appear directly at target when it becomes eligible; this is an intentional quality-limit compromise. No intermediate animation values are persisted or broadcast. Clock differences can shorten or skip animation; authoritative final state is unaffected.

Player projection uses an explicit rig allowlist: global environment, permitted current sources and transition metadata. It excludes saved scenes, descriptions, active/previous IDs and restore snapshots. Hidden/unavailable/unplaced parent lights are excluded; effective visible floor/position are projected from current parents. Scene activation cannot publish hidden floors or parent identities through preset contents. Existing authorization, atomic revisions, command receipts, save/templates/import/export and restart persistence remain in force.

Manual C checklist: create Daylight, customize/save Night Watch, attach a Fire Elemental emitter and save a third scene. Activate with a two-second transition; check smooth environment/emitter changes and no camera/floor/combat/terrain change. Edit active lighting, verify Unsaved changes, explicitly save or save as new. Rename/duplicate/delete and restore previous. Reload, reconnect and join late as a player; verify final atmosphere, permitted sources and no scene management/private presets. Enable reduced motion and change quality locally. Test fullscreen and tablet-sized modal keyboard/focus. Independently measure physical-device shadow cost before raising budgets. This is visual atmosphere, never illumination-based gameplay.

## Delivery inventory and operational notes

- Shared data/domain: `lighting.ts`, `lightingState.ts`, `lightingScenes.ts`, `dungeon.ts`, `domain.ts` add bounded schemas, transforms, snapshots/commands, history and the player allowlist.
- Rendering: `LightingEnvironment3D`, `PointLights3D`, `lightingAnimation`, `lightingResources`, the opt-in `AtmosphericSurfaceMaterial` and existing image/texture/terrain adapters retain the single canvas, caches, geometry and camera.
- UI: `LightingEnvironmentPanel`, `LightingSourcesPanel`, `LightingScenesPanel`, `DungeonBuilder`, existing D5 quality menu and scoped floor/form styles reuse the established inspector, buttons, menus, confirmation and native modal patterns. The scene dialog uses shared `ledger-form` tokens. The feature matrix/audit/migration plan record actual locations; the canonical design rules need no conflicting exception.
- Server: existing game-command execution stamps scene activation time and preserves map history during derived attachment updates. No new REST endpoint or separate lighting service/store is introduced. Existing command receipts/revisions remain authoritative.
- Coverage: shared lighting/source/scene tests, real PostgreSQL/socket lighting tests and four browser workflows cover scene values/materials, legacy parity, transforms, privacy, save/reload/restart, histories, transitions/reduced motion, viewer budgets, camera/scene identity, focus and tablet form dimensions. The complete existing suites also exercise combat, libraries, images, terrain, levels and GLBs.

Existing database backups already include encounter/template JSON; lighting needs no extra storage directory or migration runner step. New map JSON fields require the updated binary: preserve untouched map copies and coordinate a rollback that might otherwise use older strict readers. No deployed map, production account, binary asset or campaign state was modified. No deployment or 6.1 work occurred.

Remaining limits: active-floor atmosphere and emitters are shared across stacked visible geometry; source/scene/payload budgets are deliberate; optional point shadows are costly and immediate shadow flags cannot be interpolated; missing scene references are skipped; clocks and local budgets can shorten/skip transitions. Direct property edits snap the affected animation channel and mark the saved scene dirty. Radius and horizontal offsets use map squares (one world unit); heights use the existing five-feet-per-world-unit elevation convention. Physical GPU/tablet profiling and real screen-reader acceptance remain manual. No illumination rules, vision, fog or other gameplay effects are introduced.
